## 2. Слабые места сервиса (до доработки)

### 2.1 Дубли не обрабатывались вообще — **главная проблема**

Старый сервис выдавал ровно столько строк, сколько было в источнике: 436 → 436.
При этом в файле:

* **36 групп** строк с полностью совпадающим названием компании (43 лишние строки).
  В том числе целый повторяющийся блок строк 353–388, дублирующий строки 3–38.
* Ещё группы, которые видны только по **хендлу в скобках**:
  `distribuidora_alpha_mx` (строка 6) и
  `Distribuidora Alpha (distribuidora_alpha_mx)` (строка 394) — это одна компания.
* **17 e-mail** и **39 телефонов** встречаются больше чем у одной строки — то есть
  компании продублированы под разными названиями
  (`Alpha Store` / `Alpha Store Colombia`, `BetaPro` / `Beta Pro México (betapro.mx)`).

Итог по всем трём признакам: **57 групп, 81 лишняя строка**, 436 → **355**.

| Размер группы | Групп |
|---|---|
| 2 строки | 38 |
| 3 строки | 15 |
| 4 строки | 3 |
| 5 строк | 1 |

| Что совпало | Групп |
|---|---|
| название + телефон | 19 |
| только название | 16 |
| e-mail + название + телефон | 8 |
| e-mail + телефон | 4 |
| только e-mail | 3 |
| только телефон | 5 |
| e-mail + название | 2 |

**Дубли не просто лишние — они несут данные.** Повторный блок 353–388 частично
«обеднён»: там есть строки, где потеряны e-mail и телефон. Объединение
восстанавливает контакты: строк **совсем без контактов** становится
**35 → 14**, а в 5 группах объединение заполнило поле, пустое у первой строки.

> **Решение.** Сервис теперь всегда формирует **два файла**: полный (с дублями,
> строка-в-строку как в источнике) и чистый (объединённый), плюс CSV-отчёт
> «какие строки в какую склеились и по какому признаку». Признаки объединения
> (название / e-mail / телефон / сайт) включаются галочками.

### 2.2 Перепутанные поля — значения молча терялись

В исходном файле значения регулярно лежат не в своей колонке:

| Строка | Колонка | Что там лежит | Старое поведение |
|---|---|---|---|
| 63 | Phone | `+56911110008 / https://www.instagram.com/alpha.cl/` | телефон взят, **ссылка выброшена** |
| 69 | Phone | `https://www.linkedin.com/company/alpha-group / +507 200 0000_x0003_` | телефон взят, ссылка выброшена |
| 70–78 | Phone | **только URL**, телефона нет вообще (9 строк) | ячейка → **пусто**, данные потеряны |
| 85 | Website | `+52 55 1111 0006` | `get_url()` не смог → **пусто** |

Всего: **15 ссылок в телефонной колонке** и **1 телефон в колонке сайта**.

Хуже того — старая логика была **необратимой**: колонка, определённая как
телефонная, показывалась в интерфейсе только как «Phone 1/2/3». Исходный текст
ячейки становился недоступен. Если бы автоопределение ошиблось (см. 2.3),
вся колонка была бы потеряна без возможности вручную её перекинуть.

> **Решение.** Каждая ячейка теперь разбирается на «атомы» по содержимому:
> **`@` → e-mail**, **только цифры/`+`/скобки → телефон**, **домен с точкой и
> реальной зоной → сайт**. Значение не своего типа переносится в подходящее
> поле (e-mail → Work/Home/Other E-mail, ссылка → Corporate/Other Website,
> номер → Mobile/Home/Other Phone), а если такое значение там уже есть —
> отбрасывается как дубликат. Всё это пишется в отчёт `field_fixes_report.csv`
> с номером строки. На реальном файле: **2 переноса + 10 отброшенных дублей**.

### 2.3 Автоопределение телефонных колонок давало ложные срабатывания

Старый код:

```python
PHONE_HEADER_KEYWORDS = ('phone', 'tel', 'whatsapp', 'wa', 'cel', ..., 'contact', 'number')
def looks_like_phone_header(header):
    return any(k in header.lower() for k in PHONE_HEADER_KEYWORDS)   # подстрока!
```

Проверка по подстроке означала, что телефонной колонкой считались, например:

* `Contact email` → содержит `contact`
* `Warehouse` → содержит `wa`
* `Hotel name` → содержит `tel`

А определение по содержимому (`порог 0.3`, «есть хоть один похожий на номер
кусок») срабатывало на индексах, датах, ценах и ID.

В сочетании с 2.2 это давало полную потерю колонки: `Contact email` разбирался
бы на «Phone 1/2/3» (пусто), а сами адреса стали бы недоступны.

> **Решение.** Ключевые слова длиной ≤3 (`wa`, `tel`, `cel`) сравниваются
> **по целому слову**, а не по подстроке; `contact` убрано. Добавлен
> стоп-список (`mail`, `website`, `zip`, `id`, `date`, `price`, …), причём
> короткие стоп-слова тоже сравниваются по слову — чтобы `Provider phone`
> (содержит `id`) не был заблокирован. Определение по содержимому подняли
> с 0.3 до **0.5** и оно теперь считает вердикт по **всей ячейке**
> (`classify_value`), а не по наличию цифр. И главное — даже при ошибке
> определения данные **не теряются**: e-mail и ссылки из телефонной ячейки
> сохраняются отдельно и доступны для переноса.

### 2.4 Телефоны: «+» подставлялся вслепую

`normalize_phone()` добавлял `+` любому номеру с 8+ цифрами:

```
3311110004  →  +3311110004      # такого кода страны не существует
6611110009  →  +6611110009      # это мексиканский номер, нужен +52
```

На реальном файле так «починено» **108 номеров** — то есть примерно **треть**
телефонов в результате была в невалидном международном формате.

> **Решение.** Добавлена настройка **«код страны по умолчанию»**. Номера без
> `+` и короче 11 цифр получают указанный код: `6611110009` → `+52 6611110009`.
> В статистике колонки теперь отдельно видно `✓ok` / `+добавлен` / `код страны`
> / `⚠ invalid`, а на шаге сопоставления показывается предупреждение
> «108 номеров были без "+" и без кода страны».

### 2.5 Лимит в 3 телефона на ячейку обрезал данные молча

`MAX_PHONES_PER_CELL = 3`. В файле есть ячейка с **5 номерами** — 2 из них
просто исчезали, без единого сообщения.

Вдобавок автосопоставление раскладывало телефоны только по трём полям
(Mobile / Home / Other), так что 4-й и 5-й под-столбец оставались
несопоставленными и тоже терялись.

> **Решение.** Лимит поднят до 5; превышение считается (`stats.overflow`) и
> выводится предупреждением. Автосопоставление «переливает» лишние столбцы
> в последнее поле цепочки (Other Phone Number) — значения склеиваются через
> запятую, но не пропадают.

---

### 2.6 Один номер попадал в два поля

Если в источнике один и тот же номер лежал и в «Mobile», и в «Home», в
результат он писался дважды. То же с e-mail и сайтами.

> **Решение.** `_strip_cross_field_duplicates()` — после сборки строки
> повторы вычищаются между полями одного типа, остаётся первое вхождение.

### 2.7 Эксплуатационные проблемы

| Проблема | Было | Стало |
|---|---|---|
| Сессии в памяти | росли бесконечно, не чистились | TTL 6 ч + лимит 50 сессий (`SESSION_TTL_SECONDS`, `MAX_SESSIONS`) |
| Папка `uploads/` | не чистилась, лид-данные лежали вечно | удаляется вместе с сессией + подчистка «осиротевших» папок |

| Формулы в CSV | `=`, `+`, `@` в начале ячейки — инъекция формулы при открытии в Excel | опциональная защита (по умолчанию выкл., чтобы не ломать телефоны с `+`) |

## 3. Что осталось известным ограничением

* **Объединение по телефону может склеить разные компании.** На реальном файле
  таких групп 5, и 4 из них — явно одна и та же компания под разными
  названиями. Но, например, строки 294 (`Gamma Insumos SRL.`) и 321
  (`Delta Medical RD`) делят номер `+1 809-555-0100` — это может
  быть общий колл-центр. Поэтому: **всегда сверяйтесь с
  `duplicates_report.csv`**, а при сомнениях снимайте галочку «по телефону».
* **Объединение по сайту выключено по умолчанию** — несколько компаний могут
  иметь общий сайт-агрегатор.
* Комментарии и текстовые поля при объединении склеиваются через `, ` — для
  длинных комментариев результат может быть громоздким.
* Список TLD (`KNOWN_TLDS`) намеренно неполный: иначе инстаграм-хендлы вида
  `alpha.cw` считались бы сайтами. Если в вашем файле есть сайты в экзотических
  зонах — добавьте зону в список (см. `docs/DEVELOPER.md`).
